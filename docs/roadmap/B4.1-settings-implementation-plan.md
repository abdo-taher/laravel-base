# B4.1 Settings Implementation Plan

## 1. Responsibility
The Settings package provides a strongly-typed, runtime-adjustable global configuration store. It is intended for project-wide toggles, limits, and administrative preferences that must change without a redeployment.

## 2. Settings vs Configuration
- **Configuration (Foundation):** Static, deploy-time values (e.g., database credentials, service URLs). Immutable at runtime.
- **Settings (Platform):** Dynamic, runtime values (e.g., maintenance mode toggle, max upload size). Mutable at runtime and persisted in the database. 
Settings definitions explicitly declare defaults; they do *not* automatically bridge to `Foundation.Configuration` to avoid unnecessary tight coupling in the MVP.

## 3. Scope Model
**GLOBAL ONLY.**
There is no `tenant_id`, `user_id`, or polymorphic scope. The schema and contracts strictly evaluate globally.

## 4. Core Model
- **`SettingType` (Enum):** `STRING`, `INTEGER`, `FLOAT`, `BOOLEAN`.
- **`SettingKey` (VO):** Immutable, non-empty alphanumeric string identifier.
- **`SettingDefinition` (VO):** Maps a key to a type, optionally defining a default value and whether it is required.
- **`SettingsRegistry` (Interface):** Defines the active `SettingDefinition` list for the project.
- **`SettingsReader` (Interface):** Reads values safely.
- **`SettingsWriter` (Interface):** Writes/resets values safely.
- **`SettingsRepository` (Interface):** Combines Reader and Writer.

## 5. Semantics
- **Read known key:** Returns persisted value. If missing, returns default. If missing and required (no default), throws `SettingValueMissing`.
- **Read unknown key:** Throws `SettingNotDefined`.
- **Write valid value:** Validates type against definition. Persists via last-write-wins.
- **Write wrong type:** Throws `SettingTypeMismatch`.
- **Write unknown key:** Throws `SettingNotDefined`.
- **Reset/Delete:** Removes the persisted override, restoring the definition's default behavior on next read.

## 6. Persistence Architecture
- **Schema:** A single `settings` table with columns: `key` (string, primary key), `type` (string), `payload` (string/json text), `created_at`, `updated_at`.
- **Adapter:** `DatabaseSettingsRepository` using Laravel's `Illuminate\Database\ConnectionInterface` query builder.
- **Boundary:** Eloquent is NOT exposed. DB exceptions are caught and wrapped in `SettingPersistenceFailed`.

## 7. Dependencies
- **Foundation:** Zero mandatory dependencies. Does not strictly require Configuration, Identity, or Audit for the core MVP.
- **Platform:** No dependencies on other Platform packages.

## 8. Extension Model
- A `SettingContributor` interface will be defined to allow modules to supply `SettingDefinition` lists.
- Runtime discovery/wiring via the ExtensionRegistry is structurally planned but actively deferred until a downstream module uses it.

## 9. Security, Concurrency, and Cache
- **Security:** Explicitly NOT a secret store. Passwords/keys must not be stored here.
- **Concurrency:** Simple last-write-wins database updates. No optimistic locking for MVP.
- **Cache:** No caching in MVP. Correctness is isolated to database truth.

## 10. Module Manifest
- **Namespace:** `Base\Platform\Settings`
- **Capability:** `settings.runtime` (version 0.1.0)
- **Data Ownership:** Owns the `settings` table.
