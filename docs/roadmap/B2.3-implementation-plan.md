## Classes and Contracts

- `CapabilityContract` — framework-free marker for resolved capability implementations.
- `CapabilityProviderContract` — framework-free provider contract returning a CapabilityContract.
- `CapabilityResolver` — registration and resolution boundary using provider definitions.
- `CapabilityName` — validated readonly dot-delimited capability identifier.
- `CapabilityVersion` — validated readonly semantic version with comparison helpers.
- `CapabilityProviderDefinition` — readonly name/version/provider/metadata/priority/strategy registration.
- `CapabilityResolutionResult` — readonly requested capability, constraint, required state, and optional selected provider.
- `InvalidCapabilityDefinition` — invalid name, version, metadata, priority, or strategy failure.
- `CapabilityResolutionFailed` — missing, incompatible, or ambiguous resolution failure.
- `InMemoryCapabilityRegistry` — deterministic registration store and resolver.
- `VersionConstraintMatcher` — exact/caret compatibility foundation; full semantic solver is deferred.

## Dependencies

- PHP standard library only.
- Public contracts contain no Laravel types.
- The existing Laravel service provider is the only container integration.
- No dependency on ModuleManager, ExtensionRegistry, DependencyResolver, Manifest runtime, database, or project code.

## Registration

Every definition records:

- capability name;
- semantic version;
- provider contract;
- metadata;
- integer priority;
- optional explicit strategy key.

Registration order must not determine resolution results.

## Resolution

- A single compatible provider resolves.
- Exact and caret version constraints are supported initially.
- Missing required capabilities fail closed.
- Missing optional capabilities return an unresolved result.
- Existing but incompatible providers are rejected.
- Multiple compatible providers are rejected unless an explicit strategy key uniquely selects one.
- Provider priority is exposed for a later deterministic strategy engine but does not silently break ambiguity in B2.3.

## Tests

### Positive

- Single provider resolves.
- Compatible caret version resolves.
- Optional capability absence returns an unresolved result.
- Explicit strategy selection resolves one matching provider.
- Metadata and priority are preserved.

### Negative

- Missing required capability.
- Incompatible version.
- Ambiguous compatible providers.
- Invalid capability name/version and unsupported constraint.

### Value Objects

- All required capability values are readonly and preserve registration/resolution state.
