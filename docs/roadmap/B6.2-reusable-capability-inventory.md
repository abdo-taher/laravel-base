# B6.2 Reusable Capability Inventory

## 1. Objective
Create a complete inventory of reusable cross-project capabilities required for a practical Laravel Base. Identify missing capabilities before Product modules and the Project Factory are built, enabling automated dependency resolution (e.g., selecting `Products` automatically provisions `Media` and `Files`).

## 2. Current Implemented Capabilities
- **Foundation**: `manifest.parse`, `capabilities.registry`, `dependencies.resolve`, `extensions.registry`, `access-control.authorize`, `audit.log`, `health.check`, `observability.instrument`.
- **Platform**: `settings.runtime`, `files.storage`, `notifications.dispatch`, `feature-flags.evaluate`.
- **Specialized**: `outbound-webhooks.dispatch`.

## 3. Classification Rules
- **Foundation**: Low-level technical primitives/runtime contracts.
- **Platform**: Broadly reusable application capabilities.
- **Specialized**: Optional advanced/provider-heavy capabilities.
- **Laravel-native**: Solved sufficiently by the framework; no Base abstraction needed.
- **Product**: Business/domain semantics.
- **Deferred**: Potentially useful but no current justification.

## 4. Media Target Concept
Media is NOT raw file storage. It provides a lifecycle for opaque reference codes (e.g., `med_xxxxx`) attached to polymorphic business entities via defined slots (single/collection).
Upload -> generates reference -> Business Request passes reference -> Media capability resolves, validates, and syncs the attachment to the polymorphic owner.

## 5. Media MVP vs Future
- **MVP**: Opaque reference generation, polymorphic attachment (sync/attach/detach), single/multiple slots, MIME/size validation, cleanup of orphaned references.
- **Future**: Presigned uploads, chunking, antivirus scanning, dynamic conversions/thumbnails.

## 6. Verification/OTP
Classified as **Platform** (P1). Requires generating codes, limits, expiration, and verifying targets. It will NOT own delivery; it delegates to an injected `notifications.dispatch` capability (Dependency UNRESOLVED pending formal Verification planning).

## 7. Notifications Adapters
No new capability abstraction is needed. `Platform.Notifications` is sufficient. New channels (SMS, Push, Email) will be implemented as Infrastructure adapters for the existing dispatcher.

## 8. SMS
Classified as an adapter for `Platform.Notifications`. No standalone `sms.send` capability.

## 9. Email
Classified as **Laravel-native** / `Platform.Notifications` adapter. Laravel's `Mail` provides sufficient infrastructure transport.

## 10. Push
Classified as an adapter for `Platform.Notifications` (P1/P2). Device routing may require a separate Specialized capability (see Devices).

## 11. Devices
Classified as **Platform candidate** (P1). Manages device identifiers, push tokens, platforms, and invalidation tied to a Principal. Depends on `identity.current-principal`. Do not freeze as Specialized yet.

## 12. Identity Gaps
Registration, Login, Logout, API Tokens, Password Reset. Classified as **Laravel-native**. Sanctum/Passport and Fortify solve this without requiring Base abstractions. `Foundation.Identity` defines the `Principal` contract only.

## 13. API Tokens/Sessions
Classified as **Laravel-native**. Infrastructure adapters will map framework concepts to the Identity semantic contract.

## 14. Localization
Classified as **Laravel-native**. No semantic value in abstracting the framework translation system.

## 15. Location/Reference Data (Countries, Cities)
Classified as **Product/Deferred**. Too project-specific for generic Base core.

## 16. Query/Filtering
Classified as **Host Convention**. No Base abstraction required. Spatie Query Builder or similar conventions will be used at the Presentation boundary.

## 17. API Response Conventions
Classified as **Host Convention**. Base packages will throw semantic Exceptions; the Host application will format API responses.

## 18. Upload Lifecycle
Direct/Temporary uploads are part of the **Media** capability MVP. Presigned/chunked uploads are **Deferred**.

## 19. Search
Classified as **Deferred**. Re-evaluate when a concrete reusable need exists.

## 20. Inbound Webhooks
Classified as **Deferred**.

## 21. Import/Export
Classified as **Product-owned / Deferred**.

## 22. Payments
Classified as **Product / Specialized (Deferred)**.

## 23. Maps/GIS
Classified as **Specialized (Deferred)**.

## 24. Cache/Queue/Scheduler
Classified as **Laravel-native**. No wrapper needed.

## 25. Security/Secrets
Classified as **Foundation.Security / Deferred**. `SensitiveValue` exists; a full secrets manager is deferred.

## 27. Required Dependency Graph
- `Media` requires `files.storage`
- `Verification` requires `notifications.dispatch` (UNRESOLVED)
- `Devices` requires `identity.principal`

## 28. Optional Dependency Graph
- None currently specified for MVP.

## 29. P0/P1/P2 Matrix
- **P0**: `Media`
- **P1**: `Verification`, `Devices`
- **P2**: `Push Adapter`, `SMS Adapter`
- **Deferred**: `Search`, `InboundWebhooks`, `Payments`

## 30. Must-Have Before Product
**Media** (`Platform.Media` providing `media.attachments`) MUST be completed before practical Product modules can be implemented, as nearly all domain models (Catalog, User Profiles, etc.) require standard polymorphic attachment semantics.

## 31. Must-Have Before Factory
The complete **Capability Catalog** and dependency resolution logic must exist before the Project Factory to allow correct selection orchestration, but P1/P2 implementations can follow later.

## 32. Deferred Capabilities
Search, Inbound Webhooks, Imports/Exports, Payments, GIS, generic Secrets Manager.

## 33. Recommended Revised Roadmap
1. B6.2.1: Implement `Platform.Media` (P0)
2. B6.3: Minimal Product Reference Module (using Media) & B6 Freeze
3. B7.0: Project Factory / CLI Composition tooling (using the Capability Catalog)
