# B4.3 Platform.Notifications Implementation Plan

## 1. Objective
Design the minimum generic Platform.Notifications capability representing notification INTENT and DISPATCH abstractions. It provides a business-neutral, framework-independent, and independently usable boundary for outbound communications (e.g., email, SMS, push) without coupling to product domains, templating engines, or identity structures.

> **Implementation Status:** Implementation started on 2026-08-25. Validating architecture boundaries and building pure PHP models.

## 2. Scope
- Abstract message and intent representations.
- Abstract generic delivery targets (channel + address).
- Core synchronous dispatch routing.
- Strictly fail-closed failure semantics.
- Infrastructure boundaries for generic channel adapters.

## 3. Non-Goals
- No Product concepts (e.g., campaigns, invoices, orders).
- No mandatory dependency on Foundation.Identity or Foundation.Audit.
- No database persistence (no logs, no recipient tables).
- No template engine or rendering (consumers supply resolved subjects/bodies/payloads).
- No generic Laravel Queue/async wrappers in the core API.

## 4. Architectural Boundaries
Platform.Notifications resides entirely within `Base\Platform\Notifications`. It depends on zero other Platform or Foundation packages. It strictly shields its public API from `Illuminate`, `Symfony\Mailer`, and provider SDKs.

## 5. Notification Intent Model
The notification intent is represented by a `NotificationMessage` value object. It encapsulates what is being sent. The MVP model is strictly minimal and typed:
- `$body` (non-empty string)
- `$subject` (optional non-empty string)

**Explicit Restriction:** Unrestricted `array<string,mixed>` bags or arbitrary `payload` parameters are strictly prohibited. This prevents arbitrary objects, resources, provider SDK payloads, domain models, or secret-bearing structures from crossing the Notifications Public boundary. Provider-specific payloads, template variables, Blade/Markdown rendering, attachments, structured arbitrary metadata, and channel-specific options are explicitly deferred.

## 6. Target/Recipient Model
The package models raw delivery targets via the `ChannelAddress` value object, tying a `ChannelName` to a target string.

**Validation Ownership Boundary:**
- `ChannelAddress` (Core) enforces *only generic invariants* valid for every channel: non-empty channel, non-empty address string, and rejection of obvious control/null characters. It MUST NOT understand email, phone, SMS, push-token, or provider-specific syntax.
- Channel-specific target validation (e.g., verifying an email format) strictly belongs to the selected `NotificationChannel` adapter during dispatch.

One notification intent targets one `ChannelAddress` per dispatch call, preventing complex partial-failure batch models in the core.

## 7. Channel Model
- `NotificationChannel` interface defines the contract for infrastructure adapters.
- Implementations (e.g., `LaravelMailChannel`) register with the `NotificationDispatcher` (or a `ChannelRegistry`).
- The dispatcher matches the `ChannelAddress->channelName` to the registered channel.
- Duplicate registrations overwrite or throw based on registry strictness (throw on duplicate is preferred).
- Unknown channels throw an `UnknownNotificationChannel` exception.

## 8. Content/Message Model
Content crosses the boundary as pre-resolved, structured plain text via `NotificationMessage`. No Laravel `Mailable` or blade templates are exposed. Templating is explicitly deferred; if consumers want to use Laravel Blade, they render it in the Application layer before constructing the `NotificationMessage`.

## 9. Dispatch Model
The primary contract is `NotificationDispatcher`:
```php
public function dispatch(NotificationMessage $message, ChannelAddress $target): void;
```
It accepts one message and one target, resolving the channel and delegating. It returns `void` upon successful acceptance by the channel.

## 10. Delivery Result Semantics
The dispatcher returns `void`. We explicitly acknowledge that infrastructure adapters usually only guarantee provider *acceptance*, not final device *delivery*. Providing a "Delivered" enum is a false semantic. If the provider rejects the payload synchronously, an exception is thrown.

## 11. Failure Semantics
The core is strictly **fail-closed**. Exception semantics are mapped precisely:
- Structurally invalid `ChannelAddress` (e.g. empty) -> `InvalidChannelAddress`
- Unknown `ChannelName` -> `UnknownNotificationChannel`
- Valid generic address but invalid for the selected channel (e.g. malformed email passed to MailChannel) -> `InvalidChannelAddress` (thrown by adapter)
- Provider/backend rejection or infrastructure failure -> `NotificationDispatchFailed`

**Security Rule:** Exceptions must not expose the raw target value or provider credentials. PII and secrets must be scrubbed from exception messages crossing the Public boundary.

## 12. Sync/Async Ownership
Core dispatch is **synchronous**. The Public API knows nothing about queues. Async ownership belongs outside Notifications: consumers may dispatch Laravel Jobs that subsequently call `NotificationDispatcher`, or an infrastructure decorator can handle queuing transparently behind the `NotificationDispatcher` contract.

## 13. Retry Ownership
Retries are owned by the channel infrastructure (e.g., SDK internals) or the queue worker environment. The Notification core does not implement retry loops.

## 14. Persistence Decision
**No database persistence.** The B4.3 MVP does not log notifications to the database.

## 15. Identity Optional Integration
Foundation.Identity is purely optional. A future product-layer service (e.g., `UserNotifier`) could accept a `Principal`, extract their email, construct a `ChannelAddress`, and call the `NotificationDispatcher`. Notifications itself remains ignorant of Identity.

## 16. Audit Optional Integration
Foundation.Audit is purely optional. Dispatch activity can be audited later by wrapping the dispatcher in an `AuditingNotificationDispatcher` decorator at the infrastructure composition level, avoiding mandatory structural coupling.

## 17. Extension Model
ExtensionRegistry integration is deferred. Channels can be registered manually via DI (e.g., injecting the registry and calling `register()` in a ServiceProvider).

## 18. Security/Privacy Model
- `NotificationMessage` must not contain secrets.
- `ChannelAddress` contains PII. Core exceptions (e.g., `NotificationDispatchFailed`) mask or omit the raw address to prevent PII leakage in application logs.
- Provider credentials remain strictly inside infrastructure adapters.

## 19. Idempotency Decision
Idempotency is deferred. Provider-level idempotency can be implemented in the channel adapters. Core caller-generated idempotency keys are not required for MVP.

## 20. Proposed Public API
```php
namespace Base\Platform\Notifications\Public;

// Value Objects
class ChannelName { ... }
class ChannelAddress { ... }
class NotificationMessage { ... }

// Contracts
interface NotificationDispatcher {
    public function dispatch(NotificationMessage $message, ChannelAddress $target): void;
}
interface NotificationChannel {
    public function name(): ChannelName;
    public function send(NotificationMessage $message, string $address): void;
}
interface ChannelRegistry {
    public function register(NotificationChannel $channel): void;
    public function get(ChannelName $name): NotificationChannel;
}

// Exceptions
class NotificationException extends \RuntimeException {}
class UnknownNotificationChannel extends NotificationException {}
class InvalidChannelAddress extends NotificationException {}
class NotificationDispatchFailed extends NotificationException {}
```

## 24. Deptrac Implications
`Base.Platform.Notifications` will be added to `deptrac.php` with no outward `accesses()` rules (completely isolated).

## 25. Testing Strategy
- **Unit**: Verify ValueObject immutability, `ChannelAddress` string handling, and dispatcher routing logic.
- **Architecture**: Prove zero Laravel/Symfony/Flysystem leaks in `Public/`.
- **Integration**: Prove a Laravel Mail infrastructure adapter successfully formats and passes data to Laravel's `Mailer` without leaking types backward.

## 26. Acceptance Criteria
- Answers all 16 architectural review questions positively.
- `composer architecture` passes with 100% boundary safety.
- Exposes no Product domain language.

## 27. Deferred Concerns
- Templating.
- Database Logging / Receipts.
- Passive Extension discovery.
- Advanced Idempotency.
- In-App / Database inbox channels.

## 28. Explicit Implementation Sequence
1. Core Value Objects (`ChannelName`, `ChannelAddress`, `NotificationMessage`).
2. Public Contracts (`NotificationDispatcher`, `NotificationChannel`).
3. Core Exceptions.
4. Application Dispatcher (`DefaultNotificationDispatcher`).
5. Infrastructure Adapter (e.g., `LaravelLogChannel` or `LaravelMailChannel` for testing).
6. Service Provider & Module Manifest.
7. Deptrac registration and Testing.

## 29. Frozen Architectural Decisions
The following constraints are explicitly frozen and confirmed for B4.3:
- Zero mandatory Base dependencies.
- One target per dispatch.
- Synchronous core dispatch.
- Dispatch returns void.
- Successful return means only synchronous adapter/provider acceptance, NOT physical delivery.
- No queue abstraction.
- No retries in core.
- No persistence.
- No Identity dependency.
- No Audit dependency.
- No ExtensionRegistry runtime wiring.
- No core idempotency key.
- No template engine.
- No arbitrary payload/metadata bag.
- No provider SDK types in Public.
- No Laravel Notification/Mailable types in Public.
