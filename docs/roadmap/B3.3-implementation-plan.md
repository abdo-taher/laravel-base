# B3.3 Identity Foundation — Implementation Plan

## Status

IMPLEMENTED — VALIDATION PASSED

---

## 1. Identity Ownership

Identity Foundation owns:

- the `Principal` model (authenticated identity, framework-free)
- the `PrincipalId` identifier (typed string, domain-owned)
- the `PrincipalType` value object (e.g. `user`, `system`, `api-key`)
- the `Authenticator` contract (credential verification boundary)
- the `AuthenticationResult` value object (success/failure)
- the `Credentials` marker contract (mechanism-agnostic)
- the `CurrentPrincipal` contract (active principal retrieval)
- the `PrincipalEnricher` extension contract (safe profile contribution)
- the `AuthenticationFailed` exception (fail-closed)

Identity Foundation does **not** own:

- roles, permissions, authorization policies (→ AccessControl)
- customer/vendor/provider profile fields (→ project extensions)
- wallet, product, order concepts (→ product modules)
- tenant business rules (→ Tenancy)
- session storage, cookie management (→ Laravel Infrastructure)
- JWT/OAuth/Sanctum/Passport mechanics (→ Infrastructure adapters)
- secret storage (deferred)

---

## 2. Principal Model

A `Principal` is a readonly, framework-free value object representing an
authenticated identity at a single point in time.

```
Principal
  id:   PrincipalId      — typed wrapper around a non-empty string
  type: PrincipalType    — value object: 'user' | 'system' | 'api-key'
```

It carries no profile fields (name, email, avatar, etc.) — those belong
to project-owned extensions. It carries no roles or permissions — those
belong to AccessControl.

`PrincipalId` is an Identity-owned typed string. It is **not** promoted
to SharedKernel. Identifiers are inherently domain-specific and different
packages will have different validation rules. A `CapabilityName` and a
`PrincipalId` are not the same concept.

`PrincipalType` is a named value object with known base types defined as
constants. Project extensions may introduce additional types through the
extension contract.

### Why not a generic `Identifier<T>` in SharedKernel?

The SharedKernel CRITICAL RULE requires genuine multi-package need with
incompatible-if-duplicated semantics. `PrincipalId` is Identity-specific.
Future `TenantId`, `AuditEventId`, `OrderId` will carry different
validation rules and equality semantics. Forcing all identifiers through
a SharedKernel abstraction would create artificial coupling between
unrelated concepts.

## 3. Authentication Contract

```
Authenticator
  authenticate(Credentials): AuthenticationResult
```

`Credentials` is a marker interface. Concrete implementations
(`EmailPasswordCredentials`) carry the credential data. The `Authenticator`
implementation verifies them and returns either a successful result with
a `Principal` or throws `AuthenticationFailed`.

Fail-closed: `AuthenticationFailed` is always thrown on invalid
credentials. No null return. No boolean flag.

No assumption about the storage backend. No assumption about the
verification algorithm. The adapter registered by the service provider
implements `Authenticator` using Laravel's auth internals — this stays
in Infrastructure.

---

## 4. Current Principal Contract

```
CurrentPrincipal
  get(): Principal         — throws AuthenticationRequired when not authenticated
  find(): ?Principal       — returns null when not authenticated (safe)
  isAuthenticated(): bool
```

This is the contract other packages (Audit, Observability) will consume.
It replaces direct coupling to Laravel's `Auth::user()`.

The Laravel adapter (`LaravelCurrentPrincipal`) lives in Infrastructure
and reads from Laravel's `Auth` guard. It is bound in the service
provider. Public contracts remain Laravel-free.

`AuthenticationRequired` is thrown by `get()` when called in an
unauthenticated context — fail-closed.

---

## 5. Credentials

`Credentials` is a marker interface (no methods). Concrete types carry
the actual data:

- `EmailPasswordCredentials` — email string + password string

`EmailPasswordCredentials` is in `Public/ValueObjects/` because it is
the stable cross-boundary credential shape for email-based auth.
Password is held as a plain string — the `Authenticator` implementation
is responsible for secure verification (bcrypt comparison, etc.).
The package does not handle hashing. It does not store passwords.

---

## 6. Extension Points

`PrincipalEnricher` is a Public extension contract:

```php
interface PrincipalEnricher
{
    public function enrich(Principal $principal): Principal;
}
```

Project extensions (e.g., `extensions/Base/Identity/`) implement this to
attach additional context to a principal without modifying Identity
internals. The `EnrichablePrincipal` wrapper returned by the enrichment
pipeline is still a `Principal` (same interface/VO).

In B3.3 enrichment is passive — the enricher contract is exposed but no
runtime pipeline is wired. The service provider does not auto-discover
enrichers. This is consistent with B3.2's approach to
`ConfigurationSourceContributor`.

---

## 7. Persistence Ownership

Identity conceptually owns the `users` table.

**In B3.3, no new migrations are introduced.** The existing
`database/migrations/0001_01_01_000000_create_users_table.php` is a
Laravel host-level migration for `App\Models\User`. Identity will
eventually own this table through its own migration, but migrating
ownership now would create disruptive churn without functional benefit.

The `module.json` declares `users` as owned but defers the migration
claim to a future task. This is noted as technical debt.

The `App\Models\User` Eloquent model remains in `app/` (host scope).
Identity's Infrastructure layer (`IdentityUser`) will eventually be a
separate Eloquent model under `Identity/Infrastructure/` — deferred.

The public `Principal` value object never exposes the Eloquent model.
The `Authenticator` Infrastructure adapter reads from the existing
Laravel User model internally; this does not cross the Public boundary.

## 8. Laravel Adapter Boundaries

**Infrastructure only:**

- `LaravelAuthenticator` — implements `Authenticator` using Laravel's
  `Auth::attempt()` and wraps the result into a `Principal`.
- `LaravelCurrentPrincipal` — implements `CurrentPrincipal` by reading
  from `Auth::user()`.

Neither class appears in `Public/`. The service provider binds both
contracts to their Infrastructure implementations.

| Contract | Kind | Purpose |
|---|---|---|
| `Authenticator` | interface | Credential verification — returns AuthenticationResult or throws |
| `CurrentPrincipal` | interface | Active principal retrieval for the current request context |

| `EmailPasswordCredentials` | readonly value object | Email+password credential pair |

| `AuthenticationRequired` | exception | Unauthenticated access to `CurrentPrincipal::get()` |

## 16. Implementation Notes

**Issues resolved during implementation:**

1. `Authenticator.php` comment contained the word `Eloquent` — the architecture
   test scans Public contract source files for forbidden Eloquent references.
   The comment was reworded to remove the word while preserving intent.

2. `LaravelAuthenticator` initially used `Illuminate\Contracts\Auth\Guard` which
   lacks `attempt()`. Changed to `Illuminate\Contracts\Auth\StatefulGuard` in
   both the adapter and test mocks. An explicit `instanceof StatefulGuard` check
   was added so the adapter fails closed if a non-stateful guard is configured.

3. `LaravelAuthenticator` called `$this->auth->guard()->user()` a second time
   after already holding `$guard`. Fixed to reuse the same `$guard` variable.

# B3.3.1 — Identity Contract Hardening

## Status

IMPLEMENTED — VALIDATION PASSED

## Changes

### 1. AuthenticationResult invariant

Removed the `success: bool` property from `AuthenticationResult`.

Before: `AuthenticationResult(principal: Principal, success: bool = true)`
After:  `AuthenticationResult(principal: Principal)`

An `AuthenticationResult` now always and only represents successful
authentication. The invalid state `success=false` is no longer
representable. Failure is signalled exclusively by throwing
`AuthenticationFailed`. The `success()` named constructor is kept as a
readability alias (`AuthenticationResult::success($principal)` ≡
`new AuthenticationResult($principal)`).

### 2. Credentials abstraction

Added `Credentials` marker interface to `Public/Contracts/`.

`EmailPasswordCredentials` now implements `Credentials`.

`Authenticator::authenticate()` signature changed from
`EmailPasswordCredentials` to `Credentials`.

`LaravelAuthenticator` explicitly type-checks for `EmailPasswordCredentials`
and throws `AuthenticationFailed::unsupportedCredentials()` for any other
type — fail closed.

`AuthenticationFailed` gained a new named constructor:
`unsupportedCredentials(string $credentialsClass): self`

### 3. Persistence ownership clarification

No migrations moved. README updated with an explicit transitional state
table and a **mandatory future task** marker. The current `App\Models\User`
and root Laravel migration are documented as transitional placeholders,
not approved architecture.
