# B3.4 AccessControl Foundation — Implementation Plan

## Status

PLANNED

---

## 1. Authorization Model

AccessControl answers a single question:

> Can this Principal perform this Action on this Resource?

The model is **attribute-based policy evaluation** (ABAP), not RBAC.
Policies are stateless functions that receive the principal, action, and
resource and return an explicit decision. There is no global state, no
ambient authority, and no hidden side effects.

The evaluation flow:

```
Principal + Action + ResourceType → PolicyEvaluator → AuthorizationDecision
```

### Why not RBAC?

Foundation must contain no product-specific business rules. Roles like
`admin`, `vendor`, `customer` are product concepts. Embedding RBAC in
Foundation creates coupling between the authorization infrastructure and
business domain.

Instead, AccessControl provides the **evaluation engine**. Business
modules contribute **policies** that map permissions, roles (if they
exist), or any attribute to authorization decisions. If a project needs
RBAC, it implements it as a policy contributor — not as a Foundation
primitive.

---

## 2. Permission Representation

```
Permission — readonly value object
  value: string  — dot-notated, non-empty (e.g. 'wallet.view', 'identity.authenticate')
```

Permissions are plain string-backed value objects. They are constructed
by business modules, not hard-coded in AccessControl. AccessControl
validates format (non-empty string) but does not validate semantics.

Business modules own their permission names. AccessControl owns the
`Permission` type and the evaluation infrastructure.

---

## 3. Role Model

**Roles are NOT introduced in B3.4.**

Justification:

- Foundation must be business-free. Role names are inherently
  business-specific.
- RBAC can be layered on top via policy contributors by business modules
  that define their own role ↔ permission mappings.
- Adding roles now would create pressure to add `admin`, `moderator`,
  etc. — which violates the Foundation rule.
- The policy evaluation model is sufficient for B3.4. Roles can be
  introduced in a future Platform or Product module.

## 4. Policy / Evaluator Contracts

### AuthorizationChecker (Public contract)

The primary public interface consumed by other modules:

```php
interface AuthorizationChecker
{
    public function check(Principal $principal, Permission $permission, ?ResourceType $resource = null): AuthorizationDecision;
    public function isGranted(Principal $principal, Permission $permission, ?ResourceType $resource = null): bool;
    public function demand(Principal $principal, Permission $permission, ?ResourceType $resource = null): void; // throws AccessDenied
}
```

- `check()` — returns an explicit decision value object
- `isGranted()` — convenience boolean, defaults to deny
- `demand()` — throws `AccessDenied` on deny (fail-closed)

### AuthorizationPolicy (Public contract)

The extension point for policy contribution:

```php
interface AuthorizationPolicy
{
    public function evaluate(Principal $principal, Permission $permission, ?ResourceType $resource = null): ?AuthorizationDecision;
    public function supports(Permission $permission, ?ResourceType $resource = null): bool;
}
```

- `evaluate()` returns `null` when the policy abstains (does not apply)
- `supports()` enables efficient dispatch

### PermissionContributor (Public contract)

Extension point for modules to declare their permissions:

```php
interface PermissionContributor
{
    /** @return list<Permission> */
    public function permissions(): array;
}
```

Business modules implement this to register permission names with the
system. AccessControl aggregates them for discovery/validation purposes.
This is compatible with the existing contributor model
(`ConfigurationSourceContributor` pattern).

## 5. Value Objects

### Permission

```php
final readonly class Permission
{
    public function __construct(public string $value)
    {
        // validates non-empty, non-whitespace
    }
}
```

### ResourceType

```php
final readonly class ResourceType
{
    public function __construct(public string $value)
    {
        // validates non-empty, non-whitespace
    }
}
```

Identifies the type of resource being accessed (e.g. `'wallet'`,
`'order'`). Not the specific resource instance — instance-level
authorization is a concern for business-module policies.

### AuthorizationDecision

```php
final readonly class AuthorizationDecision
{
    private function __construct(
        public bool $granted,
        public string $reason,
    ) {}

    public static function allow(string $reason = 'Allowed by policy.'): self;
    public static function deny(string $reason = 'Denied by policy.'): self;
}
```

Explicit, immutable decision. No tri-state. No null. Named constructors
enforce semantics.

## 6. Exceptions

### AccessDenied

```php
final class AccessDenied extends RuntimeException
{
    public static function forPermission(Permission $permission): self;
    public static function missingPrincipal(): self;
}
```

Thrown by `demand()` and by fail-closed defaults. Message must not
reveal internal policy details.

## 7. Relationship to Identity Principal

AccessControl depends on **Identity Public contracts only**:

- `Base\Foundation\Identity\Public\ValueObjects\Principal`
- `Base\Foundation\Identity\Public\ValueObjects\PrincipalId`
- `Base\Foundation\Identity\Public\ValueObjects\PrincipalType`

AccessControl does NOT:

- Modify Identity internals
- Depend on `App\Models\User`
- Own authentication
- Import `CurrentPrincipal` — the caller resolves the principal and
  passes it to `AuthorizationChecker`

The `AuthorizationChecker` accepts a `Principal` parameter. It does not
internally resolve the current user. This keeps AccessControl
stateless and testable without a request context.

---

## 8. Persistence Ownership

**No persistence in B3.4.**

The runtime model is entirely in-memory. Policies are contributed by
modules at boot time. Permission registrations are aggregated from
contributors in memory.

If persistence is needed in the future (e.g. database-backed permission
assignments), it will be introduced as a separate migration owned by
AccessControl with table prefix `access_control_`.

## 9. Extension Model

Business modules extend AccessControl through two contributor contracts:

1. **`PermissionContributor`** — declares permission names
2. **`AuthorizationPolicy`** — contributes authorization evaluation logic

These follow the existing contributor pattern established by
`ConfigurationSourceContributor` in Configuration.

### Example: Wallet Module Contributing Permissions

```php
// modules/Wallet/WalletPermissionContributor.php
final class WalletPermissionContributor implements PermissionContributor
{
    public function permissions(): array
    {
        return [
            new Permission('wallet.view'),
            new Permission('wallet.transfer'),
            new Permission('wallet.deposit'),
        ];
    }
}
```

### Example: Wallet Module Contributing a Policy

```php
// modules/Wallet/WalletAuthorizationPolicy.php
final class WalletAuthorizationPolicy implements AuthorizationPolicy
{
    public function supports(Permission $permission, ?ResourceType $resource = null): bool
    {
        return str_starts_with($permission->value, 'wallet.');
    }

    public function evaluate(
        Principal $principal,
        Permission $permission,
        ?ResourceType $resource = null,
    ): ?AuthorizationDecision {
        // Business logic here — AccessControl never sees this
    }
}
```

Modules register contributors through service providers or through
`module.json` declarations. Wiring to the full ExtensionRegistry runtime
is deferred to post-B3 (consistent with Configuration's approach).

## 10. Application Layer — PolicyEvaluator

```
PolicyEvaluator (internal)
  — aggregates registered AuthorizationPolicy instances
  — iterates policies in order
  — first non-null decision wins
  — if all policies abstain → deny (fail-closed)
```

This is the only Application-layer component. It implements
`AuthorizationChecker` and is bound in the service provider.

### Conflict Resolution

First-match wins. If no policy returns a decision, the default is
**deny**. This is the simplest fail-closed model. Weighted priority,
deny-overrides, or permit-overrides strategies can be introduced later
via a strategy interface — but B3.4 ships with first-match-or-deny.

---

## 11. Laravel Adapter Boundary

**No Laravel Gate/Policy adapter in B3.4.**

Justification:
- The Public contracts are sufficient for consumers.
- Laravel Gate bridging would add complexity without a concrete consumer.
- When a Gate adapter is needed, it belongs in `Infrastructure/` and
  bridges `AuthorizationChecker` to `Illuminate\Contracts\Auth\Access\Gate`.

**Service Provider** (Infrastructure):

`AccessControlServiceProvider` binds:
- `AuthorizationChecker` → `PolicyEvaluator`

It does NOT wire policy contributors automatically (deferred to
ExtensionRegistry runtime, consistent with Configuration).

## 14. Tests

### Positive

- `Permission` wraps a non-empty string correctly.
- `Permission` equality by value.
- `ResourceType` wraps a non-empty string correctly.
- `ResourceType` equality by value.
- `AuthorizationDecision::allow()` produces a granted decision.
- `AuthorizationDecision::deny()` produces a denied decision.
- `PolicyEvaluator` returns allow when a policy grants.
- `PolicyEvaluator` returns deny when a policy denies.
- `PolicyEvaluator` passes principal, permission, and resource to policy.
- `isGranted()` returns true for an allowed decision.
- `demand()` does not throw for an allowed decision.
- Identity `Principal` can be evaluated through `AuthorizationChecker`.

### Negative

- `Permission` rejects empty string.
- `ResourceType` rejects empty string.
- Missing/null principal scenario: `AccessDenied::missingPrincipal()` is available.
- `PolicyEvaluator` denies when no policies are registered (fail-closed).
- `PolicyEvaluator` denies when all policies abstain (fail-closed).
- `demand()` throws `AccessDenied` on deny.
- Product-specific permissions not hard-coded in AccessControl.
- Public API has no Laravel/Eloquent coupling (architecture scan).

### Architecture tests

- No Public contract imports `Illuminate\*`.
- No Public contract references Eloquent, Gate, Request, Auth types.
- Public contracts expose no product-specific vocabulary.
- Value objects are readonly.

### Framework independence

- All Public value objects instantiable without a Laravel container.

## 17. Deferred Concerns / Technical Debt

- **Role-based access control:** Deferred to business/platform modules.
  Not a Foundation concern.
- **Laravel Gate adapter:** Deferred until a concrete consumer exists.
- **Database-backed permission assignment:** Deferred. Runtime-only in B3.4.
- **Automatic contributor discovery:** Deferred to full ExtensionRegistry
  runtime. Manual registration via service providers for now.
- **Priority/ordering of policies:** First-match-or-deny in B3.4. Strategy
  pattern for alternative conflict resolution deferred.
- **Resource instance authorization:** B3.4 supports `ResourceType` (type-level).
  Instance-level authorization (e.g. "can user 5 edit order 42") is a business
  concern implemented in business module policies.
- **Caching of authorization decisions:** Deferred. No caching layer in B3.4.
