# B3.7 Health Foundation - Implementation Plan

## 1. Goal
Implement a minimal, framework-independent Health Foundation package that provides the boundaries for liveness, readiness, and detailed health reporting.

## 2. Health Model
- **HealthStatus**: Enum representing `healthy`, `degraded`, or `unhealthy`.
- **HealthMetadata**: Strict structured data container (rejecting objects/closures/resources to prevent leakages), identical in security posture to `LogContext`.
- **HealthCheckResult**: The individual outcome of a single check.
- **HealthReport**: The aggregated outcome containing an overall `HealthStatus` and individual `HealthCheckResult`s.

## 3. Semantics
- **Liveness**: "Is the process alive?" Evaluates only checks that explicitly declare themselves as affecting liveness. Failures indicate the process should be killed/restarted.
- **Readiness**: "Can this application safely serve traffic?" Evaluates checks declaring readiness. Required dependencies failing will cause readiness to fail.
- **Details**: Evaluates all registered checks (liveness, readiness, and details-only) to provide a complete picture for diagnostics. Does not expose inner exception traces or secrets.

## 4. Contracts & Registration
- **HealthCheck**: Interface defining `name()`, `isLiveness()`, `isReadiness()`, and `check()`.
- **HealthRegistry**: Interface for modules to register their checks during boot.
- **HealthReporter**: Evaluates the registry to produce `Liveness`, `Readiness`, and `Details` reports.

## 5. Failure Aggregation
- The `HealthReporter` acts as a safe boundary. If a `HealthCheck::check()` throws a `Throwable`, the reporter catches it and converts it into an `UNHEALTHY` result.
- Exception stack traces are deliberately omitted from the `HealthCheckResult` to prevent exposing connection strings or credentials. Only the exception class name is exposed in the reason.
- Overall status becomes `unhealthy` if *any* evaluated check is `unhealthy`. It becomes `degraded` if *any* evaluated check is `degraded` and none are `unhealthy`. Otherwise, it is `healthy`.

## 6. Laravel & Adapter Boundaries
- The Public and Application layers are strictly framework-independent.
- Routing (e.g., `/health/live`) and Laravel-specific checks (e.g., Eloquent DB check) are explicitly excluded from Foundation and belong in Infrastructure/Presentation layers of consuming packages.

## 7. Deferred Concerns
- **Timeouts**: No async/timeout engine is provided in the Foundation. Checks that might hang must implement their own internal timeouts (e.g., cURL timeouts) or be wrapped by a future async adapter.
- **Observability**: Health does not depend on Observability. If checks need to log their failures, they should depend on Observability individually.
