# B6.3 Verification & Devices Architecture Plan

## 1. Planning Decision
Architecture is frozen for `Platform.Verification` and `Platform.Devices`. Implementation can proceed based on this specification.

## 2. Verification Classification
**Platform Module** (`Platform.Verification`). It models generic one-time challenge semantics (OTP, confirmations) independent of product-specific workflows.

## 3. Verification Dependency Decision
**Zero Dependencies.** Verification will strictly handle challenge generation, expiration, rate limits, and verification validation. It will NOT own delivery. `issueAndSend` will not exist in the core package. The caller is responsible for retrieving the plaintext code upon issue and delegating to `Platform.Notifications`. This maximizes decoupling and testability.

## 4. Verification Target Model
A framework-independent `VerificationTarget` value object.
- `type` (string: e.g., 'email', 'phone', 'principal')
- `value` (string: e.g., 'user@example.com', or a hash for privacy)
Verification will persist the `value` directly. If the caller requires PII privacy (since Verification doesn't send the code, it doesn't need plaintext), the caller passes a hash.

## 5. Verification Purpose Model
A `VerificationPurpose` value object carrying a namespaced string (e.g., `auth.login`, `profile.change-email`). Purpose ensures a code issued for one action cannot be reused for another.

## 6. Code Generation/Storage Decision
- **Generation**: Cryptographically secure numeric/alphanumeric strings (via `random_int`).
- **Storage**: Plaintext codes are NEVER stored. The DB stores a hash (e.g., `password_hash`).
- Native PHP hashing is sufficient; no `Foundation.Security` dependency is required.

## 7. Exact Lifecycle
- **ACTIVE**: `consumed_at` is null, `attempts < max_attempts`, `expires_at > now`.
- **CONSUMED**: `consumed_at` is set.
- **LOCKED**: `attempts >= max_attempts`.
- **EXPIRED**: `expires_at <= now`.
No explicit string `state` column is strictly required if derived via these attributes.

## 8. Resend Semantics
Issuing a new challenge for an exact `Target` + `Purpose` combination will implicitly **invalidate** any currently ACTIVE challenge for that pair. The cooldown policy (rate limiting) is delegated to the host application (e.g., Laravel Throttle) rather than abstracting a new RateLimiter inside Verification.

## 9. Attempt-Limit Semantics
The `attempts` counter increments on every failed check. Reaching `max_attempts` locks the challenge permanently.

## 10. Verification Concurrency Model
The `verify()` method must utilize atomic database locking (`lockForUpdate`). Two simultaneous verify requests will serialize on the DB row; the first successful one sets `consumed_at`, causing the second to fail.

## 11. Verification Persistence Shape
Table: `verification_challenges`
- `id` (ulid/uuid)
- `reference` (string, e.g., `vrf_xxxxx`)
- `target_type` (string)
- `target_value` (string)
- `purpose` (string)
- `code_hash` (string)
- `attempts` (int)
- `max_attempts` (int)
- `expires_at` (timestamp)
- `consumed_at` (timestamp, nullable)
- `created_at` / `updated_at` (timestamps)

## 12. Verification Public API
Minimal API Contracts:
- `VerificationIssuer`: `issue(VerificationTarget $target, VerificationPurpose $purpose, int $length = 6, int $ttlSeconds = 900, int $maxAttempts = 3): IssuedChallenge` (Returns Reference and Plaintext Code)
- `VerificationVerifier`: `verify(VerificationReference $reference, string $code): void` (Throws exceptions on failure)

Value Objects: `VerificationTarget`, `VerificationPurpose`, `VerificationReference`, `IssuedChallenge`.

## 13. Verification Client/Application Flow
1. App calls `issue()`.
2. App receives `IssuedChallenge`.
3. App sends the code via `Notifications`.
4. App returns the opaque `VerificationReference` to the HTTP client.
5. Client submits `reference` + `code`.
6. App calls `verify(reference, code)`.

## 14. Devices Classification
**Platform Module** (`Platform.Devices`). It tracks device metadata, platforms, and push tokens. Push delivery infrastructure belongs to adapter packages, but device lifecycle management is a core generic capability.

## 15. Devices Identity Dependency Decision
**REQUIRED `Foundation.Identity`**. Devices are inherently tied to Principals (users) for routing notifications. `Platform.Devices` will explicitly depend on Identity to reference `PrincipalId`.

## 16. Device Identifier Model
`DeviceId`: Stable, client-generated opaque identifier uniquely identifying the physical device or application installation.

## 17. Push-Token Model
`PushToken`: Provider-issued mutable push token (e.g., FCM token).

## 18. Device Registration/Update Semantics
`register(PrincipalId $owner, DeviceId $device, DevicePlatform $platform, ?PushToken $token)`:
If `DeviceId` already exists, its `owner`, `platform`, `push_token`, and `last_seen_at` are updated. This handles a device logging out of User A and logging into User B.

## 19. Token Uniqueness Semantics
A `PushToken` must be unique across all active devices. If a new device claims an existing push token, the previous device's token is nulled out to prevent duplicate message routing to stale device records.

## 20. Logout/Invalidation Semantics
`unregister(DeviceId $device)` sets `push_token = null` and `active = false`. The row remains for historical audit purposes.

## 21. Device Persistence Shape
Table: `devices`
- `id` (ulid/uuid)
- `device_id` (string, unique index)
- `principal_id` (string, index)
- `platform` (string)
- `push_token` (string, nullable, unique index)
- `active` (boolean)
- `last_seen_at` (timestamp)
- `created_at` / `updated_at` (timestamps)

## 22. Device Public API
`DeviceRegistry`:
- `register(PrincipalId $owner, DeviceId $device, DevicePlatform $platform, ?PushToken $token): void`
- `unregister(DeviceId $device): void`
- `touch(DeviceId $device): void`
- `getDevicesForPrincipal(PrincipalId $owner): array<Device>`

Value Objects: `DeviceId`, `DevicePlatform`, `PushToken`.

## 23. Push Integration Decision
Push delivery will be a `NotificationChannel` adapter (e.g., `Specialized.Notifications.FCM`). The adapter will depend on `Platform.Notifications` and `Platform.Devices`. When asked to notify a Principal, the adapter queries `Platform.Devices` to resolve the Principal into active `PushToken`s.

## 24. SMS Decision
SMS is a `NotificationChannel` adapter. No standalone Base capability.

## 25. Email Decision
Email is a `NotificationChannel` adapter utilizing Laravel Mail. No standalone Base capability.

## 26. Final Required Dependency Graph
- `Platform.Verification` -> NONE
- `Platform.Devices` -> `Foundation.Identity`
- `SMS Adapter` -> `Platform.Notifications`
- `Email Adapter` -> `Platform.Notifications`
- `Push Adapter` -> `Platform.Notifications`, `Platform.Devices`

## 27. Capability Names
- `verification.codes`
- `devices.manage`

## 28. Factory Resolution Example
A Product module requires `verification.codes` and `devices.manage`.
The ModuleManager provisions:
- `Platform.Verification`
- `Platform.Devices`
- `Foundation.Identity` (automatically resolved as a dependency of Devices).

## 29. Recommended Implementation Order
Implement **Verification first, then Devices**. They can be separate PRs/batches, allowing rapid cadence. 

## 30. Whether these block Product Reference Module
**NO.** A minimal Product Reference Module (e.g., Blog or Catalog) can be fully realized using `Media`, `Settings`, and `Notifications`. Verification and Devices are crucial for full-scale authentication modules but do not block architectural validation of Product boundaries.

## 31. Security Decisions
- **Verification**: Codes are securely generated and strictly hashed in DB. Resends invalidate previous challenges. Atomic locking prevents concurrent consumption. Brute force mitigated via `max_attempts`.
- **Devices**: Token uniqueness ensures stolen or recycled tokens don't spam multiple users. Unregister cleans push tokens.
