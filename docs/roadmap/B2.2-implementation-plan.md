IMPLEMENTED — VALIDATION PASSED

## Scope

Implement only the Base Foundation DependencyResolver package: immutable dependency graph construction, architecture-direction validation, cycle detection, and deterministic provider-first ordering from validated Manifest objects.

## Classes

- `DependencyGraph` — Public read-only graph contract exposing nodes and edges.
- `DependencyResolver` — Public contract accepting validated Manifest values and returning a ResolutionResult.
- `DependencyNode` — readonly node containing the component identity, category, version, namespace, and source Manifest.
- `DependencyEdge` — readonly consumer-to-provider edge with target type, version constraint, and required state.
- `ResolutionResult` — readonly graph plus deterministic providers-first ordering.
- `DependencyResolutionFailed` — Public exception exposing accumulated graph validation errors.
- `ImmutableDependencyGraph` — internal immutable implementation of the graph contract.
- `ManifestDependencyResolver` — graph builder, validator, cycle detector, and deterministic topological sorter.

## Dependencies

- Depends only on `Base\Foundation\Manifest\Public\ValueObjects`.
- Package dependencies resolve by manifest name.
- Capability dependencies resolve against capability declarations present in the supplied manifests; no registry state is created.
- Multiple capability providers fail closed because provider-selection strategy belongs to the future CapabilityRegistry.
- No external package, database, Laravel type, ModuleManager, CapabilityRegistry, or ExtensionRegistry appears in Public contracts.

## Validation Rules

- Required package/capability targets must be present.
- Optional missing targets do not create edges and do not fail resolution.
- Every dependency must contain a non-empty version constraint; full semantic constraint solving is deferred.
- Dependency direction must follow the accepted category matrix.
- Duplicate declarations from the same consumer to the same target are rejected.
- Duplicate manifest names are rejected.
- Circular graphs are rejected.

## Ordering

- Ordering is topological and provider-first.
- Nodes simultaneously eligible for ordering are sorted lexicographically by manifest name.
- Input iteration order must not affect the result.

## Tests

### Positive

- Valid dependency graph contains expected nodes and edges.
- Valid capability dependency resolves to its unique provider.
- Deterministic provider-first ordering is stable across different input order.
- Missing optional dependency does not fail.

### Negative

- Missing required dependency.
- Circular dependency.
- Forbidden Foundation-to-Platform direction.
- Duplicate dependency declaration.
- Empty dependency version constraint.
- Ambiguous capability provider.

### Value Objects

- Graph result, nodes, and edges expose expected immutable data.
