# B2.5 ModuleManager Foundation — Implementation Plan

## Status

IMPLEMENTED — VALIDATION PASSED

## Scope

Implement the Base Foundation ModuleManager package as an orchestration
layer only.

Responsibilities:
1. Module discovery — discover declared package/module manifests by
   scanning filesystem paths for `module.json` files.
2. Manifest validation orchestration — delegate to existing Manifest
   package (ManifestReader).
3. Dependency resolution orchestration — delegate to DependencyResolver.
4. Capability registration orchestration — delegate to CapabilityRegistry.
5. Extension registration orchestration — delegate to ExtensionRegistry.
6. Boot ordering foundation — expose deterministic initialization order
   via a ModuleBootPlan value object.

Full lifecycle management is deferred.

## Public Contracts

- `ModuleDiscovery` — given one or more filesystem search paths,
  returns `list<Manifest>` by finding and reading every `module.json`
  under those paths.
- `ModuleBootPlan` — value object exposing the deterministic ordered
  list of `ModuleIdentifier` values and access to per-module
  `ModuleState`.
- `ModuleManager` — single orchestration entry point:
  `boot(iterable<string> $searchPaths)` returns a `ModuleBootPlan`.

## Value Objects

- `ModuleIdentifier` — readonly, holds `name` (string) and
  `category` (string). Equality is by name.
- `ModuleState` — readonly, holds identifier and a state string
  (`discovered`, `invalid`, `ready`). Foundation only; no full
  lifecycle.

## Application (internal)

- `FilesystemModuleDiscovery` — iterates search paths, calls
  `ManifestReader` for each found `module.json`. Fails closed on
  unreadable/invalid manifests (throws `ModuleDiscoveryFailed`).
- `DefaultModuleBootPlan` — immutable result; holds ordered
  `list<ModuleState>`.
- `OrchestrationModuleManager` — wires discovery → manifest
  validation (via ManifestReader, which validates on read) →
  DependencyResolver → CapabilityRegistry (registers declared
  capabilities from resolved manifests) → ExtensionRegistry (registers
  declared extension points from resolved manifests) → returns
  `DefaultModuleBootPlan` built from the topological order.

## Fail-Closed Rules

- Invalid manifest → `ModuleDiscoveryFailed`.
- Duplicate module identity → `ModuleBootPlanFailed`.
- Missing required dependency → `ModuleBootPlanFailed` (from
  `DependencyResolutionFailed`).
- Dependency cycle → `ModuleBootPlanFailed`.

## Tests

## Implementation Result

B2.5 implemented the framework-free Public orchestration contracts
(`ModuleManager`, `ModuleDiscovery`, `ModuleBootPlan`), two immutable
value objects (`ModuleIdentifier`, `ModuleState`), two fail-closed
exceptions (`ModuleDiscoveryFailed`, `ModuleBootPlanFailed`), and three
Application-layer classes (`FilesystemModuleDiscovery`,
`DefaultModuleBootPlan`, `OrchestrationModuleManager`) plus internal
helpers (`ManifestCapabilityProvider`, `ManifestCapabilityToken`).

The service provider binds both `ModuleDiscovery` and `ModuleManager`
as singletons wired to their dependencies through the Laravel container.

Extension point registration from manifests is deferred until the
Manifest value object carries `extension_points` metadata (the current
`Manifest` VO does not include that field).
