## Probe Model

Each probe creates a unique directory below the operating-system temporary directory. The directory may temporarily mirror `packages/base/`, `extensions/`, and `modules/`, but it is never added to production autoloading or repository architecture configuration.

Each temporary component declares test metadata containing:

- component identifier, category, and namespace;
- capabilities provided, including public contract and provider identifier;
- capabilities required;
- optional deterministic provider resolutions at composition level.

The test-only validator checks PHP imports against component metadata and validates capability availability and provider resolution.

## Required Probes

### Expected Failures

1. An extension imports a Base internal implementation.
2. A module consumes a capability contract without declaring the capability requirement.
3. A declared required capability has no provider.
4. Multiple providers expose the same capability without a deterministic resolution strategy.

Each invalid composition must return one or more explicit validation errors.

### Expected Pass

5. A realistic composition containing Base packages, a project extension, and a Product module uses Public contracts, declares requirements, has available providers, and resolves deterministically.

The valid composition must return no validation errors.

## Architecture Rules Being Tested

- Extensions may consume Base Public extension/capability contracts but never Base internals.
- Capability requirements must be explicit rather than inferred or hidden.
- Required capabilities fail composition when no compatible provider exists.
- Multiple providers require an explicit deterministic resolution strategy.
- Product modules and extensions compose downward through Public contracts and capabilities.
- Base packages remain independent of project extensions and Product modules.

## Expected Results
