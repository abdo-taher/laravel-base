# B6.2.1 Platform.Media Implementation Plan

## 1. Objective
Design a reusable `Platform.Media` capability that abstracts temporary uploads into opaque references (`med_xxxxx`) and safely syncs them to business entities via polymorphic attachments, ensuring Product layers never deal with raw file handling during regular entity update cycles.

## 2. Files vs Media Boundary
- **Platform.Files**: Owns raw storage keys, blob reading/writing/deletion, and visibility.
- **Platform.Media**: Owns upload lifecycles, opaque reference generation, single/multiple slot validation, syncing algorithms, and orphan cleanup. Media strictly delegates raw blob operations to `files.storage`.

## 22. HTTP Endpoint Semantics
Platform.Media currently provides the internal `MediaUploader` capability. A standard `POST /media` Presentation adapter (HTTP Controller) is still required before the overall Base is considered project-ready, as the target Base experience explicitly expects upload-first/reference-later API behavior.
This is classified as a **P0 integration follow-up**. It will consume the `MediaUploader` interface and handle Framework-specific request mapping (e.g. `UploadedFile`).

## 3. Client Flow & Upload Endpoint
1. Client directly requests an upload via `POST /media` (or host-configured route).
2. Media streams to `Platform.Files` and persists an unattached `media` row in `TEMPORARY` state.
3. Client receives *only* the opaque reference: `{"reference": "med_xxxxx"}`.
4. Client passes this reference in a standard business JSON payload (e.g., `{"main_image": "med_xxxxx"}`).
5. Application derives the internal `MediaAccessScope` (e.g., from the authenticated session).
6. Business Application layer persists its entity and invokes `MediaSynchronizer::sync(...)`, passing the entity owner, current access scope, slot changes, and slot definitions.
7. `Platform.Media` validates the reference, verifies the scope, ensuring attachment security, and permanently links the reference.

## 4. Opaque Reference
- **MediaReference**: Opaque, non-sequential string (e.g., generated via cryptographic `random_bytes` + base62 encoding). This is the *only* identifier exposed to the client. No database ID, storage key, or internal token is ever exposed.

## 5. Security & Internal Access Scope
- **Upload Ownership**: A `MediaReference` alone does not grant attachment rights. To prevent User A from attaching User B's upload, an internal `MediaAccessScope` value object abstracts the context (e.g., authenticated Principal, guest session, API client).
- **Identity Agnostic**: Media does not know what the scope represents. The application supplies it during both upload (where it is stored as a string representation in the DB) and sync (where it is verified against the stored scope). Identity is NOT a dependency.
- **MIME/Size Limits**: Client filename/MIME are untrusted. Server-side detection (`finfo`) is mandatory. Path traversal is prevented via abstract storage paths. Exhaustion is mitigated via cleanup TTLs.

## 6. Lifecycle States & Reference Reuse
- **States**: `TEMPORARY` (new upload) -> `ATTACHED` (owned by 1 business entity) -> `ORPHANED` (detached/pending cleanup) -> `DELETED` (blob & row destroyed).
- **Reuse Rules**: One-owner, attach-once semantics.
  - A `TEMPORARY` reference may be attached once.
  - An `ATTACHED` reference cannot be attached to another owner.
  - An `ORPHANED` reference cannot be reused as a fresh upload reference; it only waits for cleanup.

## 7. Owner Reference Model
- Framework-independent `MediaOwnerReference` value object containing:
  - `type` (string: explicit logical name, e.g., 'product', not an Eloquent class name)
  - `id` (string: scalar UUID/ULID)

## 8. Slot Definition Model
- `MediaSlotDefinition` explicitly defines:
  - `name` (e.g., 'gallery')
  - `cardinality` (`SINGLE` or `MULTIPLE`)
  - Optional validation (allowed MIME types, max file size, max item count for collections).
- **Ownership**: The consuming module owns these declarations and passes them explicitly. Does not rely on `Settings` or `ExtensionRegistry`.

## 9. Typed Sync Input (Slot Changes)
- Avoids arbitrary `array<string, mixed>` boundaries. Introduces a minimal structured model like `MediaSlotChanges` mapping to:
  - `UNTOUCHED`: Omitted key (no action taken).
  - `CLEAR`: Explicit `null` or `[]` (detach existing media).
  - `SET reference(s)`: Explicitly provided string/array (sync final state).

## 10. Single Slot Semantics
- **SET**: Attaches new reference (detaching any existing media).
- **CLEAR (`null`)**: Detaches current media.
- **UNTOUCHED (Omitted Key)**: Leaves slot unchanged.

## 11. Multiple Slot Semantics
- **SET (Array of References)**: Defines exact final ordered state. Missing existing references are detached.
- **Duplicate References**: Rejected.
- **Order**: Preserves the exact array order passed in the request.
- **CLEAR (`[]`)**: Detaches entire collection.
- **UNTOUCHED (Omitted Key)**: Leaves collection unchanged.

## 12. Sync Security Algorithm
Before attaching a `TEMPORARY` reference, the Synchronizer verifies:
- Reference exists and is `TEMPORARY`.
- `MediaAccessScope` exactly matches the stored upload scope.
- Slot definition accepts MIME and Size.
- Collection item count limit is respected.
- Duplicate references are blocked.
`ATTACHED` and `ORPHANED` references immediately fail verification.

## 13. Detach / Orphan Policy
- Detaching media transitions it from `ATTACHED` to `ORPHANED`.
- Clears `owner_type`, `owner_id`, `slot_name`, and `sort_order`, whilst recording the `orphaned_at` timestamp.
- It does **not** synchronously delete the Files blob, avoiding destructive DB/filesystem mismatches during business updates.

## 14. Orphan Cleanup
- Cleanup handles expired `TEMPORARY` and expired `ORPHANED` media.
- Host application invokes this via Scheduler (e.g., calling a `MediaCleaner` contract).
- TTL configuration is provided by the application composition, not `Platform.Settings`.

## 15. Transaction Semantics
- The `MediaSynchronizer::sync` updates participate natively in the caller's DB transaction (assuming the same DB connection).
- The filesystem is NOT transactionally atomic.
- If the business transaction rolls back, Media attachment updates roll back, leaving the upload `TEMPORARY`. The eventual orphan cleanup will safely handle the abandoned blob. No distributed transaction guarantees are claimed.

## 16. Persistence Shape
For the single-owner MVP, a single Media-owned table:
`id`, `reference`, `storage_key`, `original_name`, `mime_type`, `size`, `state` (TEMPORARY/ATTACHED/ORPHANED), `upload_scope` (string), `owner_type` (nullable), `owner_id` (nullable), `slot_name` (nullable), `sort_order` (nullable), `timestamps`, `attached_at` (nullable), `orphaned_at` (nullable). (No Product-specific foreign keys).

## 17. Public API Direction
Minimal target objects:
- Value Objects: `MediaReference`, `MediaAccessScope`, `MediaOwnerReference`, `MediaSlotName`, `MediaSlotDefinition`, `MediaSlotChange`, `MediaSlotChanges`.
- Contracts: `MediaUploader`, `MediaSynchronizer`, `MediaCleaner`.
- Exceptions: `InvalidMediaReference`, `MediaSlotViolation`, `MediaUploadFailed`.

## 18. Factory Graph
- `Product` requires `media.attachments`.
- Factory resolves `media.attachments` -> `Platform.Media`.
- `Platform.Media` requires `files.storage`.
- Factory resolves `files.storage` -> `Platform.Files`.
- Factory provisions all three automatically.

## 19. Non-Goals & Deferred
- Conversions, image dimensions, temporary URLs, presigned S3 uploads, multi-owner pivots, and synchronous blob destruction are deferred.
