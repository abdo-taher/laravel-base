## Status

## 1. Candidate Evaluation

The critical rule requires that a primitive enters SharedKernel only when:

1. it is domain-neutral;
2. it has stable semantics;
3. multiple Base packages genuinely need the same concept;
4. duplicating it would create incompatible platform semantics.

Every candidate was evaluated against all four criteria. Justification
and rejection rationale are explicit below.

---

### Candidate: SemanticVersion

**Accepted.**

**Evidence of duplication today:**

`Manifest\Application\ManifestFactory` contains a private
`isSemanticVersion(string $version): bool` method using the regex:

```
/^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)(?:-[0-9A-Za-z.-]+)?(?:\+[0-9A-Za-z.-]+)?$/
```

`CapabilityRegistry\Public\ValueObjects\CapabilityVersion` applies the
**identical** regex to parse and expose `major`, `minor`, `patch`
components.

Both encode the same invariant — what constitutes a valid semantic
version — but do so independently.

**Why all four criteria are met:**

1. **Domain-neutral.** Semantic versioning is a technical specification
   (semver.org), not a business concept. It belongs to infrastructure,
   not product.

2. **Stable semantics.** Semver is a well-defined, externally
   standardized specification. The contract — parse a three-part version
   string, validate it, expose components — will not change for business
   reasons.

3. **Multiple Base packages genuinely need the same concept.** Manifest
   validates every `module.json` version field. CapabilityRegistry
   parses provider versions for constraint matching. DependencyResolver
   depends on Manifest versions. ModuleManager creates `CapabilityVersion`
   objects from manifest data. Every future Foundation or Platform package
   that registers capabilities or declares versions will need it. The
   concept is unavoidable across the platform foundation.

4. **Duplicating it creates incompatible platform semantics.** If the
   regex in ManifestFactory and CapabilityVersion diverge — even a
   whitespace difference or a missing capture group — a valid manifest
   version could fail capability registration, or an invalid version
   could slip through manifest validation. The platform would accept
   version strings that are inconsistently valid across packages.
   SharedKernel eliminates this class of divergence permanently.

**What moves:**

- A new `SemanticVersion` readonly value object is introduced in
  SharedKernel with parsing, validation, and comparison.
- `ManifestFactory.isSemanticVersion()` is replaced with
  `SemanticVersion::isValid()` (or `SemanticVersion::tryFrom()`).
- `CapabilityVersion` wraps or delegates to `SemanticVersion` internally
  so the CapabilityRegistry Public contract remains unchanged.
- `ManifestFactory` is an internal class; its change is not a public
  contract break.
- `CapabilityVersion` is a public contract. The change to its internal
  implementation must not alter its public API surface.

---

### Candidate: Clock contract

**Deferred.**

Zero clock usage in any current Foundation package. No current consumer
pair exists. Future consumers (Audit, Observability) are not implemented.
Introducing a Clock contract now would be speculative design.

The B3.1 CRITICAL RULE forbids speculative abstractions. Clock will be
reconsidered when the first Base Foundation package that genuinely needs
it is implemented.

---

### Candidate: Identifier abstraction

**Rejected.**

`ModuleIdentifier` is module-specific (name + category). `CapabilityName`
is a capability-specific validated string. Future `UserId`, `TenantId`,
`AuditEventId` will carry domain-specific identity semantics with
different validation rules and equality models. There is no shared
cross-package identifier concept that is both domain-neutral and
needed by multiple packages with incompatible-if-duplicated semantics.
Each package should own its identity primitives.

---

### Candidate: Result/Error primitives

**Rejected.**

All Foundation packages use typed exceptions exclusively. No
`Result<T, E>` pattern exists or is needed. Introducing it now is a
speculative abstraction. If a package genuinely adopts a Result pattern
in the future, it can be promoted to SharedKernel then.

---

### Candidate: Pagination primitives

**Rejected.**

Zero pagination usage across all Foundation packages. No Foundation
package needs pagination. Pagination is a query-layer concern relevant
to Platform (Notifications, Search) and Product modules. It does not
belong in Foundation SharedKernel.

## 3. Package Structure

```
packages/base/Foundation/SharedKernel/
├── Public/
│   ├── ValueObjects/
│   │   └── SemanticVersion.php
│   └── Exceptions/
│       └── InvalidSemanticVersion.php
├── module.json
└── README.md
```

No service provider is needed — SharedKernel exposes only value objects
and exceptions. There is nothing to bind in the Laravel container.

No `Application/` or `Infrastructure/` directories are created: there
is no internal implementation beyond the value object itself.

## 4. Public Contracts Introduced

### `SemanticVersion`

```
namespace Base\Foundation\SharedKernel\Public\ValueObjects
```

Readonly value object.

Constructor: `__construct(string $value)` — validates and parses.

Throws: `InvalidSemanticVersion` on invalid input.

Public properties (via readonly): `major: int`, `minor: int`,
`patch: int`, `value: string`, `preRelease: ?string`,
`buildMetadata: ?string`.

Static factory: `SemanticVersion::from(string $value): self`

Static predicate: `SemanticVersion::isValid(string $value): bool`

Comparison: `compareTo(SemanticVersion $other): int` — returns
negative/zero/positive.

### `InvalidSemanticVersion`

```
namespace Base\Foundation\SharedKernel\Public\Exceptions
```

`InvalidArgumentException` subclass. Named factory methods for
construction clarity.

## 5. Consumer Impact (packages that change)

### Manifest (internal change only)

`ManifestFactory.isSemanticVersion()` is replaced by
`SemanticVersion::isValid()`.

No public contract change — `ManifestFactory` is internal.

Manifest `module.json` gains a `package` dependency on SharedKernel.

### CapabilityRegistry (internal change only)

`CapabilityVersion.__construct()` delegates validation to
`SemanticVersion::from()` or `SemanticVersion::isValid()`.

`CapabilityVersion` public API remains unchanged. The `major`, `minor`,
`patch` properties and `compareTo()` method are untouched. Callers see
no difference.

CapabilityRegistry `module.json` gains a `package` dependency on
SharedKernel.

### All other packages

No change. DependencyResolver, ExtensionRegistry, ModuleManager do not
directly perform semver validation and require no update.

---

## 6. Dependency Impact

```
SharedKernel        (no Foundation deps)
Manifest            → SharedKernel (Public)
CapabilityRegistry  → SharedKernel (Public)
ExtensionRegistry   (no Foundation deps — unchanged)
DependencyResolver  → Manifest (Public) — unchanged
ModuleManager       → Manifest, DependencyResolver, CapabilityRegistry,
                      ExtensionRegistry — unchanged
```

SharedKernel has **no dependencies on other Foundation packages**.
This is mandatory: if SharedKernel had dependencies, it could not be
the lowest-level shared primitive layer.

### Deptrac updates required

- Add `Base.Foundation.SharedKernel` layer.
- Permit `Base.Foundation.Manifest` to access
  `Base.Foundation.SharedKernel`.
- Permit `Base.Foundation.CapabilityRegistry` to access
  `Base.Foundation.SharedKernel`.
- No other layer rules change.

## 7. Tests

### Positive (SemanticVersion)

- Valid versions are parsed and expose correct major/minor/patch.
- Pre-release metadata is preserved.
- Build metadata is preserved.
- `isValid()` returns true for valid strings.
- `compareTo()` correctly orders versions.
- `from()` returns identical object to constructor.

### Negative (SemanticVersion)

- Empty string is rejected.
- Two-part version rejected.
- Negative component rejected.
- Leading-zero component rejected (e.g., `01.0.0`).
- `isValid()` returns false for invalid strings.
- `InvalidSemanticVersion` is thrown with a descriptive message.

### Framework independence

- SemanticVersion has no imports from Illuminate or any framework.
  Verified by reflection / import scanning in the test.

### Immutability

- Readonly class — PHP enforces property immutability.
  Proved via `ReflectionClass::isReadOnly()`.

### Integration: Manifest still rejects invalid version strings

- ManifestFactory continues to reject manifests with invalid semver
  after the internal refactoring.

### Integration: CapabilityVersion still validates correctly

- CapabilityVersion still throws on invalid input and exposes correct
  components after the internal refactoring.

## 10. Implementation Result

One primitive introduced: `SemanticVersion` (readonly value object) and
its companion `InvalidSemanticVersion` (exception).

`ManifestFactory.isSemanticVersion()` (private method, internal) was
removed and replaced with `SemanticVersion::isValid()`.

`CapabilityVersion.__construct()` (public VO, internal implementation)
now delegates parsing to `SemanticVersion::from()` and catches
`InvalidSemanticVersion`, re-throwing as `InvalidCapabilityDefinition`
to preserve the existing public error contract unchanged.

Both `module.json` files (`Manifest`, `CapabilityRegistry`) gained an
explicit `package: SharedKernel ^0.1` dependency declaration.

The cross-package integration regression test was placed at
`tests/Unit/Packages/Base/Foundation/SharedKernelConsumerIntegrationTest.php`
(outside any package sub-layer) to avoid Deptrac layer conflicts.

No service provider was introduced — SharedKernel contains only value
objects instantiated directly.
