# B4.4 Platform.FeatureFlags Implementation Plan

## 1. Objective
Design the minimum generic `Platform.FeatureFlags` capability. The package provides a business-neutral, framework-independent boundary for semantic boolean feature toggle decisions (controlled enablement of technical/product code paths). It must be independently removable, zero-dependency, and strictly global for the MVP.

> **Implementation Status:** Implementation started on 2026-08-25. Validating architecture boundaries and building pure PHP models.

## 2. Settings vs FeatureFlags Boundary
- **Platform.Settings**: Manages runtime-adjustable typed values (strings, integers, floats, complex configurations).
- **Platform.FeatureFlags**: Manages semantic *boolean enable/disable decisions*. 
FeatureFlags must not depend on Settings, nor treat a flag as a simple `settings.get('feature.x')`. They possess distinct semantic contracts.

## 3. AccessControl vs FeatureFlags Boundary
- **AccessControl**: Answers "May this Principal perform this action?" (Authorization).
- **FeatureFlags**: Answers "Should this technical/product capability be enabled universally?" (Toggle).
A disabled/enabled feature must NEVER replace permission checks. FeatureFlags must never reference `Principal`, `Role`, `Permission`, or `Policy`.

## 4. MVP Scope
- **Boolean flags only.** 
- String variants, numeric variants, multivariate flags, and experiments are explicitly excluded.

## 5. Non-Goals
Explicitly deferred:
- Experiments and A/B testing.
- Percentage rollouts.
- User/tenant/geographic targeting.
- Rule engines and segmentation.
- Scheduled flags.
- Flag analytics and exposure tracking.
- Persistent DB store or Redis coupling.
- Admin UI interfaces.
- Feature-flag SaaS provider integration.

## 6. Flag Identity
`FeatureFlagKey` encapsulates the unique identity of a flag.
- Must be a non-empty, trimmed, immutable string.
- Defined by the consumer (code-owned).
- Must not encode database IDs or hard-coded product flags (e.g., `wallet.*` are forbidden in core).

## 7. Definition Model
`FeatureFlagDefinition` establishes the baseline code-owned intent.
- Contains a `FeatureFlagKey`.
- Contains a `defaultState` (bool).
- Remains purely immutable and business-neutral. Minimal metadata (like a short description) is omitted for MVP unless strictly necessary for developer logs.

## 8. Registry Model
`FeatureFlagRegistry` governs known flags.
- Registers definitions via manual DI mapping.
- Rejects duplicate keys deterministically (fail-closed, throws `InvalidArgumentException` or `DuplicateFeatureFlag`).
- Does not scan files or rely on `ExtensionRegistry`.

## 9. Unknown Flag Semantics
- **Throw on Unknown**: Evaluating an unregistered flag strictly throws an `UnknownFeatureFlag` exception.
- This provides critical typo-safety (e.g., `feature.new-checkuot` instead of `feature.new-checkout`) preventing developers from accidentally deploying silently-disabled code paths due to misconfiguration.

## 10. Evaluation Model
`FeatureFlagEvaluator` drives the public contract:
```php
public function isEnabled(FeatureFlagKey $flag): bool;
```
It requires no targeting context.

## 11. Context Decision
Context/Targeting is entirely deferred. The MVP assumes all flags evaluate globally (true/false) across the entire application runtime. No `EvaluationContext` object is introduced.

## 12. Default Semantics
The evaluation pipeline is deterministic:
1. Registered flag + Override exists -> Override boolean.
2. Registered flag + No override -> Definition default boolean.
3. Unregistered flag -> `UnknownFeatureFlag` exception.

## 13. Override Model
`FeatureFlagOverrideProvider` interface isolates runtime toggle variations from code-owned definitions.
- Provides a strict read-only contract: `overrideFor(FeatureFlagKey $key): ?bool`.
- Unknown override keys must NOT create implicit feature definitions. A flag MUST exist in `FeatureFlagRegistry` before it can be evaluated.
- Persists nothing in MVP. An immutable `InMemoryFeatureFlagOverrideProvider` fulfills the MVP capability, initialized statically for tests or composition.

## 14. Read/Write Responsibilities
- **Read**: `FeatureFlagEvaluator` and `FeatureFlagOverrideProvider` are strictly read-only (Primary Application boundary).
- **Write**: Explicitly absent in MVP. B4.4 exposes NO runtime mutation API. There is no `FeatureFlagWriter`, no `enable()`/`disable()`, and no `setOverride()`/`resetOverride()` capabilities. Admin mutation interfaces are entirely deferred. 

## 15. Persistence Decision
No database persistence. The core operates against in-memory registries and stores. Tables (like `feature_flags`) are strictly forbidden.

## 16. Configuration Decision
Zero dependency on `Foundation.Configuration`. Flags are registered natively via PHP closures or service providers. 

## 17. Settings Decision
Zero dependency on `Platform.Settings`. If a future infrastructure adapter reads from settings, it will sit entirely outside the core.

## 18. Identity Decision
Zero dependency on `Foundation.Identity`.

## 19. Audit Decision
Zero dependency on `Foundation.Audit`. Flag evaluation is not audited by default due to high volume.

## 20. Extension Decision
Zero dependency on `Foundation.ExtensionRegistry`. Flag discovery relies on explicit code registration.

## 21. Failure Policy
Evaluation pathways are strictly mapped to prevent accidental flag enablement:
- **Invalid key format** -> Throws `InvalidFeatureFlagKey`.
- **Duplicate definition** -> Throws `DuplicateFeatureFlagDefinition` (during registration).
- **Unknown key** -> Throws `UnknownFeatureFlag`.
- **Known default false** -> Evaluates to `false`.
- **Known default true** -> Evaluates to `true`.
- **Override false** -> Evaluates to `false`.
- **Override true** -> Evaluates to `true`.
No evaluation path may accidentally enable a feature because an error was suppressed or converted to true. Since MVP has no external infrastructure providers (no DB/Redis), speculative provider failure exceptions (like `FeatureFlagEvaluationFailed`) are deferred until actual providers exist.

## 22. Caching Decision
No cache abstraction (Redis/Memcached). The core evaluates strictly in-memory. 

## 23. Security Model
FeatureFlags dictate application flow, but possess zero authorization domain. Code paths exposed by a feature flag must still verify AccessControl privileges.

## 24. Proposed Public API
```php
// Value Objects
class FeatureFlagKey { ... }
class FeatureFlagDefinition { ... }

// Contracts
interface FeatureFlagRegistry {
    public function register(FeatureFlagDefinition $definition): void;
    public function get(FeatureFlagKey $key): FeatureFlagDefinition;
}
interface FeatureFlagOverrideProvider {
    public function overrideFor(FeatureFlagKey $key): ?bool;
}
interface FeatureFlagEvaluator {
    public function isEnabled(FeatureFlagKey $flag): bool;
}

// Exceptions
class FeatureFlagException extends \RuntimeException {}
class InvalidFeatureFlagKey extends FeatureFlagException {}
class DuplicateFeatureFlagDefinition extends FeatureFlagException {}
class UnknownFeatureFlag extends FeatureFlagException {}
```

## 25. Proposed Application Components
- `InMemoryFeatureFlagRegistry`
- `InMemoryFeatureFlagOverrideProvider` (immutable implementation for tests/composition)
- `DefaultFeatureFlagEvaluator` (combines definition default + optional override)

## 29. Testing Strategy
- **Unit**: Verify VO immutability, duplicate registry rejections, unknown flag throws, and evaluator logic (override > default).
- **Architecture**: Prove zero Laravel bounds, no DB persistence, no external Base package coupling.

## 30. Removability Analysis
The package can be deleted safely. No Foundation, Settings, Files, or Notifications layer depends on it. 

## 31. Acceptance Criteria
- Answers all 16 required review questions positively.
- `composer architecture` reports 0 violations.
- MVP relies solely on boolean flags.

## 32. Deferred Concerns
- End-user Targeting / EvaluationContext.
- Admin mutation API.
- Database override providers.
- Infrastructure provider failure handling.

## 33. Required Review Questions Answered

1. **Is MVP boolean-only?** Yes.
2. **Does core require Settings?** No.
3. **Does core require Configuration?** No.
4. **Does core require Identity?** No.
5. **Does core require Audit?** No.
6. **Does core require DB persistence?** No.
7. **Does core require Redis/cache?** No.
8. **Does core require EvaluationContext?** No.
9. **What happens for an unknown flag?** Throws `UnknownFeatureFlag`.
10. **What happens for duplicate definitions?** Throws `DuplicateFeatureFlagDefinition`.
11. **Are runtime overrides included?** Yes, but strictly via a read-only `FeatureFlagOverrideProvider` interface (and in-memory immutable implementation for composition).
12. **Where do defaults live?** Inside `FeatureFlagDefinition`.
13. **Who owns flag names?** Project developers/consumers own keys. Core remains business-neutral.
14. **Can provider failures enable a feature?** No. MVP defers provider concepts since no DB/network exists, inherently eliminating provider failures.
15. **Is FeatureFlags being used as authorization?** No. Explicit boundary distinct from AccessControl.
16. **Can package be removed independently?** Yes.
